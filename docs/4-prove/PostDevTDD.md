# Part D — Still-applicable rules from TDD §13, as built
**D-1 Transaction flow and the write phase (13.1).**
1. No write transaction is open at a dialog or after the HTTP phase: `TryValidateCustomerAddress` calls `Commit()` immediately after `AddressService.ValidateAddress` returns (harmless since the Google build writes no token), before outcome handling and before `RunModal`. `ConfirmPrivacyNotice` also commits before the approval check (the platform page may be modal).
2. The write phase is codeunit 92806, run with `if Writer.Run() then`. It re-reads the customer under `LockTable` and runs the concurrency check (the five address fields still equal the Original snapshot), writes the five values on Accept by direct assignment with `SetForceUpdateContact(true)` and `Modify(true)`, sets or resets Address Validated per FR-8 (only when `CanModify`), and inserts the log row, all in one transaction.
3. **Failure handling.** If `Writer.Run()` returns false, the orchestrator reads `GetLastErrorText()`, inserts an Error row (originals only, HTTP Status as received, Provider Message = that text, Accepted No) via `Writer.InsertLogEntry`, commits, and returns false. The customer is unchanged. This covers a Contact-sync error, a security filter or another extension's subscriber failing.
4. **Testable core.** `TryValidateCustomerAddress` does everything (preconditions, privacy check, HTTP call, dialog, write phase, logging, commits). It returns precondition and failure messages in `UserMessage` (Outcome blank when nothing was logged) and returns false for any precondition failure or Error outcome. **Exception (A3): it raises `CallerNotAllowedErr` for any caller other than this app or, in a sandbox, the test app.** `ValidateCustomerAddress` is the public entry used by the Customer Card; it shows `UserMessage` with `Message` (informational outcomes) or `Error` (errors) **after** the transaction has ended. Tests call the Try procedure and assert on Outcome, UserMessage and the log; they do not use `asserterror` for these paths.
5. User text as a format string: every `Message`/`Error` of composed text uses the Locked passthrough `ShowTextTok: Label '%1', Locked = true;` (present in codeunit 92803 and in page 92800).
6. The HTTP phase is **not** wrapped in `Codeunit.Run`; if `HttpClient.Send` raises instead of returning false (for example "Allow HttpClient Requests" off), `TryValidateCustomerAddress` raises and no Error row is written (GA-10, to be checked first thing in the sandbox round).

## F-D Behaviour summary (as built)
- Sixteen address sources: Customer plus 15. Company Information has two blocks (Main and Ship-to). The engine is table-agnostic: `"obcfgav Address Source"` maps a table number and address type to seven field numbers (Address, Address 2, City, County, Post Code, Country/Region Code, the indicator), and all reading and writing goes through a `RecordRef`.
- The public entry points `ValidateAddress` and `TryValidateAddress` run the caller check first and then `RunValidation`; `ValidateCustomerAddress` and `TryValidateCustomerAddress` are unchanged for callers and run the same `RunValidation` on the Customer. Order inside `RunValidation`: supported table and block, open the record, **Privacy Blocked** (refused, not logged, nothing sent), preconditions, privacy notice, provider call and `Commit()`, outcome handling.
- The writer re-reads the record under `LockTable`, compares the five address values with the snapshot, writes by direct assignment (never `Validate`), binds the Write Guard around the save, and writes the log row in the same failure boundary. `SaveSource` is the one place that knows the standard updates (Customer and Vendor `SetForceUpdateContact(true)`, Bank Account `BankCont-Update.OnModify`, Employee `Employee/Resource Update.HumanResToRes`).
- After the writer commits, `RunLinkedSync` (codeunit 92803) runs codeunit 92813 (`OnRun`) for **Confirmed and Not Found only, and only when `CanModify` is true** for the checked table; a failure is swallowed (F-4). Inside codeunit 92813 there are four branches (Customer, Vendor, Bank Account, Employee) and **none for Contact**: for a Contact source the update of linked records is part of the writer's `Modify(true)` (D3, F-11).
- The indicator is field 92800 on every source table (field 92801 on Company Information for the ship-to block). One number is shared across the table extensions on purpose, because standard `TransferFields` copies Customer, Vendor, Bank Account and Contact into each other by field number.
- The log keeps the address of every source; USE reads it only indirectly and page 92802 shows only rows of tables the user may read (F-12).

**codeunit 92815 Country Mgt., new and changed procedures.**
- `RegionForRecord(CountryCode: Code[10]; State: Text; PostalCode: Text; var Region: Code[2]; var CountryName: Text; var Inferred: Boolean): Boolean` — clears the three out parameters. **codeunit 92803 Address Validation.** `CheckPreconditions(var SourceRecRef; AddressType; var Region; var Inferred; var ErrorText)` reads Street, City, State, ZIP and Country with `AddressSource.GetValue` (values 1, 3, 4, 5, 6), calls `RegionForRecord(CountryCode; State; Zip; …)` (false → `NoIsoCodeText`), checks the region with `CheckRegion` when one exists, then applies the input rules of G-C by region (a guessed US region therefore meets the US rule, a guessed CA region the Canadian rule, no region the street-plus-city-or-ZIP rule). `RunValidation`: after `FillOriginal` and setting the buffer's `"Region Code"`, `AddressService.ValidateAddress` runs; **when `RegionInferred` is true, the address was not found and the buffer is `"Not Found"`, `Region` is cleared, `FillOriginal` refills the buffer (no region) and `ValidateAddress` runs once more**; then `Commit()` and the result-region check of G-C (it now also applies after the repeat because `Region` is blank).
