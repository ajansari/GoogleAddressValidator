**Kind created:** AL Test Framework (native) test codeunits, in a separate test app. No API-level automation (the extension has no API endpoints). · **Date:** 2026-10-18
**Test app:** `Google Address Validator Tests` 0.0.0.24 (previous 0.0.0.23) (`/Users/ajansari/Documents/AL/USPSAddressValidator.Tests`, package `outputAppPackage/Google_Address_Validator_Tests_0.0.0.24.app` in that folder), object IDs 92830–92849 (helpers codeunit 92830, codeunit 92831, codeunit 92835; test codeunits 92832, codeunit 92833, codeunit 92834, codeunit 92836, codeunit 92837, codeunit 92838), requires main app 1.3.0.0. **Status: 155 test procedures (codeunit 92832 = 24, codeunit 92833 = 29, codeunit 92834 = 8 as in 1.0.0.0; codeunit 92836 = 54 and codeunit 92837 = 19 added for 1.1; codeunit 92838 = 21 added for 1.2: 15 for SC-4, 4 for SC-5 and 2 for SC-5a; the catalogue in section 1 lists the first 61, section 1a summarizes the 73 new ones of 1.1, section 1b the 21 of 1.2, and `AutomatedTestGuide.md` §6 lists every one by row), written and compiled (main 1.1.0.8 and test app 0.0.0.16 compiled with 0 errors and 0 warnings; later builds main 1.2.0.4 and test app 0.0.0.23 not re-checked here), never run.** From 0.0.0.18 the library assertion `AssertLogSource` also asserts that the log entry's **Record No.** equals the non-blank parts of the source record's first key joined by ' / ' and is blank when the key is blank, as for Company Information (SC-2). 0.0.0.19 adds three tests to codeunit 92836 for FR-18.6 (`TestAcceptSetsUsCountry`, `TestConfirmedSetsUsCountry`, `TestNotFoundKeepsBlankCountry`): the count rose from 131 to 134; 0.0.0.20 and 0.0.0.21 add codeunit 92838 and move two tests from Canada to Russia (below): the count is now 149; see `AutomatedTestGuide.md` §6 notes). Nothing has been installed in a tenant yet (Gap Analysis GA-23). This document replaces the USPS-build catalogue (34 tests, kept at `docs/4-prove/USPSbuild/AutomatedTestScripts.USPSbuild-0.0.0.4.md`).

How they work: Google is never called. The tests replace the web layer with a fake (`obcfgav Fake Http Transport`, codeunit 92830) that returns queued answers (status and body) and counts calls, and, for the provider-seam tests, with a fake provider (`obcfgav Fake Address Provider`, codeunit 92835). Each test starts with `Prepare()` (clean up leftovers, reset the fakes, write a test setup with the made-up API key `test-key`, approve the privacy notice) and ends with `CleanUp()`. Test customers are numbered `GAVUT1`, `GAVUT2`, … and are deleted at the end; the 1.1 tests do the same for `GAVUT*` records in the other 15 tables. Messages are checked against copies of the main app's label texts held in the test library (codeunit 92831), so a changed label fails the test. FRD numbers below are the acceptance tests of FRD 2.0 §7.2 (1–23); "TDD A…" are the TDD test ids; "FR-n" are the FRD 2.0 functional requirements.

## 2. Maintenance commitment
These tests copy the main app's message texts and call its internal seams (`SetTransport`, `SetProvider`, the writer), so any change to a label, a precondition, a log field or the caller check has to be made in the tests in the same change, and both packages are rebuilt at the next version with the test app's dependency raised to the new main version. This document and `docs/4-prove/AutomatedTestGuide.md` §6 are revised every time a test is added, renamed or removed.

## 3. Known risks
1. **Untried under the AL Test Tool.** The 155 tests compile but nobody has run them. Expect first-run failures that are test faults, not product faults, and budget a fix round (Gap Analysis GA-23).
2. **T-04, isolation and `Commit()`.** The production code calls `Commit()` before the write phase and runs the writer with `Codeunit.Run`; the dialog handler in `TestChangedDuringDialog` also commits. Whether the AL Test Tool's runner isolation lets these commits work is unknown (TDD §13.9 item 5, Code Review T-04). If writer tests fail with a platform message about write transactions, the first suspect is the test runner's isolation, not the extension.
3. **SaaS sandbox only.** The extension's caller check lets the test app call the test seams only when the environment is a sandbox, so the tests cannot run in production, in a Docker container that does not report itself as a sandbox, or on-premises (FRD OQ-17, decided).
4. **Only in a company whose name contains TEST.** The test setup stops with an error in any other company, because the tests overwrite and delete that company's address validation setup and API key and delete all customers numbered `GAVUT*`. The earlier setup record is put back, but the stored API key is not (it is per app and unreadable from the test app): the tests replace it with `test-key` and clear it at clean-up, so re-enter the real key afterwards.
5. **Organization-wide privacy consent while tests run.** The test setup sets the privacy notice `OBCFGAV-ADDRESS` (*Google Address Validation*) to Agreed for the whole organization and puts the earlier state back at clean-up. If a run is interrupted, the state may stay Agreed.
6. **One modal handler never tried.** `TestPrivacyRefusedSendsNothing` uses a modal handler on the platform page "Privacy Notice" and its `Reject` action; whether that page and that action behave as assumed under test is unproven. A user who can approve the notice for the organization is needed (GA-23).
7. **Run as SUPER.** Changing the privacy approval state and the test setup need a user with broad permissions; run as a SUPER user in the sandbox.
