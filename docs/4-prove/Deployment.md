### 2a. Google Cloud project setup (administrator, outside Business Central)
The API key belongs to the company's own Google Cloud project. Every check is one billable request on that project.
1. In the Google Cloud console, create or choose a project for this extension.
2. **Enable billing** for the project. Google requires it even though the free allowance covers low volume (FRD appendix: 5,000 free Pro requests a month, then $17 per 1,000; at the expected volume the cost is $0).
3. **Enable the Address Validation API** for the project.
4. **Create an API key** and **restrict it to the Address Validation API**.
5. **Set a daily request cap** on that API (for example 100 per day) and **a budget alert** (for example $1). This is OQ-25, a go-live task for AJ Ansari.
6. Enter the key in Business Central (section 4) and choose **Test Connection**; it should report *The connection to Google Maps works. The API key was accepted.* Test Connection is designed to cost nothing (it sends an incomplete request); the spike must prove that it reports key, API and billing errors (OQ-28).

**Key rotation is the incident procedure.** There is no 72-hour reporting duty to a postal service any more (that was a USPS rule). If the key may have been exposed (a user with access left, the setup page seen by the wrong person, a tenant compromise): create a new key in Google Cloud, set **Enabled** off on the **Google Address Validation Setup** page, enter the new key there, delete the old key in Google Cloud, switch **Enabled** back on, and remove `OBCFGAV GAV, ADMIN` from anyone who no longer needs it. Review the Google Cloud usage report and the **Google Address Validation Log** for unexpected use.

### 2c. Countries, cost and a live probe (1.2)
1. Open **Google Address Validation Supported Countries** (Tell Me). The 40 rows are on. Switch **Enabled** off for every country whose addresses must not be sent to Google. A user who tries one gets *Address validation isn't turned on for (country). Ask your administrator to turn it on in Google Address Validation Supported Countries.*
2. The price is one price for every country: Address Validation Pro, 5,000 free requests a month in total, then about $17 per 1,000 (a billing account on India pricing gets 35,000 free). Every country shares the one free allowance and the one daily cap you set in section 2a. Only the United States and Puerto Rico return USPS delivery data.
3. **Blank Country Handling and the second request (SC-5).** Under *Let Google decide* a record without a country that looks American (a US state code and a 5- or 9-digit ZIP code) or Canadian (a postal code like A1A 1A1) is first sent with that country; if Google finds nothing, the same address is sent once more without a country, and that check is billed as two requests. Records that do not look American or Canadian are sent without a country at once (one request). Under *Use default country* every check is one request. Count this when estimating the monthly volume; a company with mostly US addresses with a state and ZIP code sees almost no second requests.
4. **Do a live probe per country you will use**, with a few real addresses (never made-up ones) and the real key: Brazil, Mexico, India and Japan especially (India and Japan are preview in Google's list; the address shapes of Brazil and Mexico, with districts, are not proven). Check what comes back: the suggestion, the state or province (a name or a code), the postal code, the second address line, and whether Accept works. Nothing of this has been seen yet.

### 4a. Retention of the validation log
- The extension registers the **Google Address Validation Log** with Business Central's Retention Policy at install, with a custom **2-year** retention period (`OBCFGAV-2Y`), applying to all records, measured on **Checked At**.
- The policy is **created disabled**. Nothing is deleted until an administrator enables it: search **Retention Policies**, open the policy for table **Google Address Validation Log**, review the period (it can be changed there), and switch **Enabled** on. This is a deliberate decision: the log is an audit trail.
- The retention job runs from the **Job Queue** as a user. That user needs **direct delete permission on the log** (included in `OBCFGAV GAV, ADMIN`) and Microsoft's retention policy permissions for the job. If the job's user lacks them, old entries are not deleted and the job fails. Confirm after enabling that the job queue entry exists, runs, and reaches status Ready.
- The log keeps the suggested address only for Confirmed and Suggestion Accepted checks (Google's storage terms). **The log keeps the record's key and address until the Retention Policy deletes the row**, also after the record itself is deleted or has been marked Privacy Blocked: deleting a customer, vendor, employee or any other record does not delete its log entries; only the retention policy does. If a data protection request needs the log rows of a person removed earlier than the retention period, an administrator has to delete them by hand (ADMIN has delete permission). The **Source** text of a row is stored text, in the language of the user who ran the check (this build ships English (United States) only); it is not translated again later.

## 5. Rollback
- **Updating to a fixed build** is the normal remedy: install the next higher version on top (SandboxInstall §6). A version, once installed, cannot be uploaded again.
- **Uninstall:** Admin Center → **Manage Apps** → the extension → **Uninstall** (or Extension Management → **Uninstall**). Details in `docs/4-prove/SandboxInstall.md` §7.
  - By default uninstalling **keeps the extension's data** — the setup record, the **Google Address Validation Log**, and the **Address Validated** value on customers — so a later reinstall finds it again.
  - With **Delete Extension Data** switched on, the extension's tables and the Address Validated field are removed. This cannot be undone. Export or keep what you need from the log first.
  - Customers' addresses are never changed by uninstalling. The API key is held in isolated storage by the extension; whether it remains after uninstall has **not been verified**. If the extension will not come back, **rotate the key** in Google Cloud (section 2a) and delete the old one.
  - The privacy notice, the retention policy entry, and the Assisted Setup entry are Business Central records; check Retention Policies, Privacy Notices and Assisted Setup after uninstalling and remove what remains if unwanted.
- **Who decides:** the administrator who owns the production environment, together with the business owner of the extension (AJ Ansari for this project).

The extension's data (setup, key, log, Customer indicators) is kept. Three upgrade codeunits run **once per company** on the first start after the upgrade: codeunit 92811 gives every old log entry a source (Customer, Main, the customer's system ID when it still exists, *Customer <No.>*), codeunit 92812 marks the linked contact of every validated customer as validated when its address equals the customer's, and (1.1.0.10) codeunit 92814 fills the new **Record No.** column of every log row from the customer number or the key of the checked record (blank when the record no longer exists).
